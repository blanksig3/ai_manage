# 任务设计与联动

## 任务设计清单

任何实质任务在修改前都必须完成本清单。清单要形成可执行契约，而不是复述用户原话。微任务压缩成一两句内联；小任务用当轮检查单；中/大任务写入 Plan 或项目唯一任务载体。长度由风险和协调成本决定，不由形式决定。

逐项回答：

1. 目标、非目标和可观察验收是什么？交付物是什么？
2. 四维路由是什么，升档理由是什么？
3. 有多个节点时最小节点图是什么？每条边的输入、输出、先后、失败传播和验证如何定义？
4. 权威输入、目标文件和直接消费者在哪里？
5. 将执行哪些读取、写入、命令或外部操作？权限是否在用户授权范围内？
6. 哪些数据必须保留，哪些内容允许删除或覆盖？备份放哪里？
7. 主要风险、动作前回退方式和失败停止条件是什么？
8. 每个节点、每条边和整体分别怎样验证？[最终完成清单](03_验证与完成.md#最终完成清单)需要哪些证据才能勾选？

小及以上任务，把清单要点用大白话摆给用户点头后再动手，说法见 [06](06_用户协作与边界.md)。

设计清单不是一次性仪式。发现消费者增加、范围扩大、证据冲突、风险变化或出现新联动节点时，立即重新路由并更新清单。

填写载体见 [templates/任务设计填写表.md](../templates/任务设计填写表.md)。

## 节点与边

说人话：节点就是这次要做的几件事，边就是它们之间怎么交接。做票链 `采集表 → 数据表 → 模板 → 全自动 → PDF` 里每个箭头都是一条边，上游没验证过的表，下游不能拿来用。

- `A → B`：B 只消费 A 已验证的输出。例：数据表没复开校验过，就不跑全自动。
- `A ↔ B`：共享契约，两边都要验证一致性。例：数据表和采集表的活动名、字段名必须同步。
- `A ∥ B`：无共享写入，可并行，在汇合点一起验收。例：两张不相干的票各自改模板。
- `A → {B,C}`：公共源扇出，必须扫描所有已知消费者。例：改根目录公共工具，要查每个调用它的项目。
- `{A,B} → C`：汇聚，前置结果缺一不可。例：主采集表和副采集表都齐了才生成数据表。

父任务只存共同目标、图、边契约和总状态；节点只存本节点状态。节点通过不等于整体通过。

两个可逆、同项目、无共享写冲突的微节点可以组成一个小型父检查单，不必各建任务卡。

## 联动闸门

执行前：输入、所有权、顺序和失败停止条件明确。

同步时：上游证据存在，格式/接口/语义符合边契约。

收口时：节点验证、边验证、整体回归三层都通过。若拓扑、消费者或风险发生变化，立即回到设计清单重新路由。

## 结构压缩

先保留中心目标和关键依赖，再按影响递减扩展细节。只有会改变决策、操作或验收的信息进入主清单；背景材料用链接引用。代码地图、模块卡和专题会议只在确有复用价值时创建，不作为默认流程。
